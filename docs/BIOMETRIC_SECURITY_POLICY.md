# ⚠️ КРИТИЧНО: Политика безопасности биометрии

## Требования ТЗ

Из технического задания (TZ.md):

> **Биометрия:** Запрещено хранить исходные фото лиц пользователей в открытом виде. Хранить только векторные представления (числовые массивы).

## Что это значит?

### ❌ ЗАПРЕЩЕНО:
- Сохранять исходные селфи пользователей в R2
- Хранить селфи в локальной файловой системе
- Архивировать фотографии лиц

### ✅ РАЗРЕШЕНО:
- Хранить 512-мерные векторы (эмбеддинги)
- Временно обрабатывать селфи для извлечения вектора
- Удалять селфи сразу после обработки

## Почему это важно?

### 1. **Невозможность восстановления**

Из эмбеддинга **НЕВОЗМОЖНО** восстановить исходное изображение лица:

```python
# Эмбеддинг - это 512 чисел:
[0.123, -0.456, 0.789, ..., 0.321]

# Это НЕ изображение!
# Это математическое представление уникальных черт лица
```

### 2. **GDPR Compliance**

Согласно GDPR, биометрические данные - это **особая категория**:
- Требуют повышенной защиты
- Могут храниться только с явного согласия
- Должны быть минимизированы (принцип data minimization)

Хранение векторов вместо фото соответствует **data minimization**.

### 3. **Меньший риск утечки**

Если БД скомпрометирована:
- ❌ С хранением селфи: злоумышленник получает фотографии лиц
- ✅ С хранением векторов: злоумышленник получает бесполезные числа

### 4. **Юридическая защита**

В случае судебных разбирательств:
- "Мы храним только векторы, не изображения"
- Меньше рисков по искам о приватности

## Реализация

### Процесс загрузки селфи:

```python
1. Пользователь загружает селфи
   ↓
2. Файл сохраняется ВРЕМЕННО в /temp/
   ↓
3. InsightFace обрабатывает → извлекает 512-мерный вектор
   ↓
4. Вектор сохраняется в PostgreSQL (vector(512))
   ↓
5. Временный файл УДАЛЯЕТСЯ (критично!)
   ↓
6. Исходное селфи больше НЕ СУЩЕСТВУЕТ
```

### База данных:

```sql
CREATE TABLE user_biometrics (
    id UUID PRIMARY KEY,
    user_id UUID REFERENCES users(id),
    
    -- ТОЛЬКО вектор!
    embedding vector(512),
    
    -- НЕ храним путь к селфи
    source_image_path VARCHAR(255) NULL,  -- Всегда NULL
    
    created_at TIMESTAMP
);
```

### Код эндпоинта:

```python
# ✅ ПРАВИЛЬНО:
@router.post("/biometrics")
async def create_biometrics(file: UploadFile, ...):
    temp_path = save_temp_file(file)
    
    try:
        # Извлекаем вектор
        embedding = face_service.process_image(temp_path)
        
        # Сохраняем ТОЛЬКО вектор
        user_bio = UserBiometrics(
            user_id=user_id,
            embedding=embedding,
            source_image_path=None  # Не храним путь!
        )
        db.add(user_bio)
        
    finally:
        # КРИТИЧНО: Удаляем файл
        os.remove(temp_path)

# ❌ НЕПРАВИЛЬНО:
@router.post("/biometrics")
async def create_biometrics(file: UploadFile, ...):
    # Загружаем в R2
    r2_key = await storage.upload_file(file, "biometrics/user.jpg")
    
    # Сохраняем путь
    user_bio = UserBiometrics(
        source_image_path=r2_key  # ❌ НАРУШЕНИЕ БЕЗОПАСНОСТИ!
    )
```

## Сравнение с альтернативными подходами

### Подход 1: Хранение хешей селфи (❌ Небезопасно)

```python
# Некоторые думают, что хэширование безопасно
selfie_hash = hashlib.sha256(file_bytes).hexdigest()

# НО: Хэш не помогает для поиска похожих лиц!
# Два селфи одного человека → разные хэши
```

### Подход 2: Хранение зашифрованных селфи (❌ Небезопасно)

```python
# Шифрование селфи и хранение в R2
encrypted_selfie = encrypt(file_bytes, key)

# ПРОБЛЕМА: Ключ хранится где-то в системе
# Если система скомпрометирована → расшифровка возможна
```

### Подход 3: Только векторы (✅ Правильно!)

```python
# Извлекаем вектор
embedding = face_service.extract_embedding(file)

# Сохраняем ТОЛЬКО вектор
# Файл удаляем навсегда

# ПРЕИМУЩЕСТВА:
# - Невозможно восстановить лицо
# - Векторный поиск работает отлично
# - GDPR compliance
```

## FAQ

### Q: Как пользователь сможет подтвердить, что это его биометрия?

**A:** Никак. Но ему это и не нужно. Биометрия используется только для поиска похожих лиц. Пользователь может в любой момент:
- Удалить биометрию: `DELETE /auth/biometrics`
- Заново загрузить селфи: `POST /auth/biometrics`

### Q: А что если пользователь захочет скачать свое селфи?

**A:** Это невозможно, так как селфи не хранится. Это **осознанное архитектурное решение** для безопасности.

Если пользователь запросит: "Дайте мне мои данные (GDPR Right to Access)", мы предоставляем:
```json
{
  "user_biometrics": {
    "embedding": [512 чисел],
    "created_at": "2025-01-12"
  }
}
```

### Q: Что если нужно показать пользователю превью его селфи в профиле?

**A:** Есть два варианта:
1. **Не показывать** (рекомендуется)
2. **Генерировать аватар** из первых букв имени или использовать иконку

```jsx
// React пример
function BiometricsStatus({ hasBiometrics }) {
  return (
    <div>
      {hasBiometrics ? (
        <div>
          <Avatar icon="✅" />
          <p>Биометрия настроена</p>
        </div>
      ) : (
        <div>
          <Avatar icon="❌" />
          <p>Биометрия не настроена</p>
        </div>
      )}
    </div>
  );
}
```

### Q: Можно ли хранить селфи хотя бы на 24 часа для аудита?

**A:** **НЕТ.** Это нарушает принцип data minimization. Если для аудита нужны логи, храните метаданные:

```json
{
  "event": "biometrics_uploaded",
  "user_id": "uuid",
  "timestamp": "2025-01-12T10:30:00Z",
  "confidence": 0.95,
  "file_size": 1024000,
  "file_type": "image/jpeg"
  // НЕ храним file_path или содержимое!
}
```

### Q: А что с медиафайлами мероприятий? Там же тоже лица?

**A:** Это **разные сценарии**:

| Тип | Хранение | Причина |
|-----|----------|---------|
| **Селфи пользователя** | ❌ НЕ хранится | Биометрический эталон (особые данные) |
| **Фото с мероприятий** | ✅ Хранится в R2 | Основной контент платформы |

Фото с мероприятий:
- Загружаются организаторами (не пользователями)
- Являются основным продуктом сервиса
- Хранятся с согласия организаторов
- Детектированные лица → только векторы (для поиска)
